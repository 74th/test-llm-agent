# Spec Delta

## Purpose

self-hosted environment の検証を再現可能にするため、リポジトリの README がリポジトリ構成・人間が行うセットアップ項目・検証手順・人間が判定すべき確認項目をどう記述すべきかを定める。

## ADDED Requirements

### Requirement: README がリポジトリの入口になる

リポジトリ直下の `README.md` が、検証に必要な情報の単一の入口でなければならない（SHALL）。README は少なくとも次の 4 つのセクションを持つ（SHALL）。

1. **構成**: `container/` と `workspace/` に何が入っているか、各ファイルの役割、コンテナ内でどこにマウントされるか。
2. **人間が設定すべき内容**: 自動化できず人間が実施する項目（後述の要件）。
3. **検証手順**: 常駐モードとセッション毎モードそれぞれの起動から片付けまでのコマンド列。
4. **人間が検証すべき内容**: claude.ai の Web UI から人間が投げるプロンプトと、その応答をどう判定するか。

README は片付け手順も持たなければならない（SHALL）。検証で発行した資格情報（GitHub PAT、サービスアカウントキー、environment key）の失効と、作成したリソースの削除を含む。

自動化できる作業（ビルド・起動）と、人間にしかできない作業（claude.ai での設定、プロンプト入力と応答の判定）が、README 上で区別されていなければならない（SHALL）。

#### Scenario: 入口が 1 つである

- **WHEN** 検証を初めて行う人が README だけを読む
- **THEN** 他の文書を探さずに、構成の把握からセットアップ、起動、判定、片付けまでを通せる

#### Scenario: 人間の作業が区別できる

- **WHEN** README を読む
- **THEN** どの手順がコマンド実行で済み、どの手順が claude.ai の画面操作や人間の判断を要するかが明示されている

### Requirement: 人間のセットアップ項目が明示される

README は、自動化できず人間が実施しなければならない項目を、実施者に必要なロールとともに列挙しなければならない（SHALL）。少なくとも次を含む（SHALL）: Owner による **Allow self-hosted environments** の有効化、environment の作成と environment key の取得、GitHub 連携の設定、GitHub PAT の発行、検証用リポジトリの用意、`terraform apply` の実行とサービスアカウントキーの発行、claude.ai からのセッション開始とプロンプト入力。

#### Scenario: 手順を初見の人が完走できる

- **WHEN** 検証環境を持たない人が README だけを見て作業する
- **THEN** 自分の権限では実施できない項目がどれかを事前に判別でき、必要な値をすべて取得できる

#### Scenario: 秘密情報の扱いが書かれている

- **WHEN** README の environment key、GitHub PAT、サービスアカウントキーの取得箇所を読む
- **THEN** それぞれをどこに保存し、どのようにコンテナへ渡すかが書かれている

#### Scenario: 片付けができる

- **WHEN** 検証を終えた人が README の片付け手順に従う
- **THEN** 発行した資格情報がすべて失効し、作成したリソースが残らない

### Requirement: 両モードで同じ確認項目を実施する

README の検証手順は、常駐モードとセッション毎モードのそれぞれについて、同一の確認項目を実施しなければならない（SHALL）。確認項目は最低限、skill が認識されること、skill の内容が回答に反映されること、MCP ツールが列挙されること、MCP ツール呼び出しが成功すること、コンテナ内の資格情報でしか到達できないリソースへセッションが到達できることを含む（SHALL）。

#### Scenario: モードごとに結果が分かれて記録される

- **WHEN** 両モードの検証を完了する
- **THEN** モード × 確認項目の組み合わせごとに、成功・失敗・未実施のいずれかが記録されている

### Requirement: 検証プロンプトと合格条件が固定されている

README は、claude.ai のセッションへ入力する検証用プロンプトを、そのままコピーして使える形で提示しなければならない（SHALL）。各プロンプトには、応答がどうなっていれば合格かの判定条件が併記されていなければならない（SHALL）。

#### Scenario: プロンプトをコピーして使える

- **WHEN** 実施者が README のプロンプトをそのままセッションに貼り付ける
- **THEN** 追加の書き換えなしに確認項目を判定できる応答が得られる

#### Scenario: 判定が実施者によってぶれない

- **WHEN** 別々の実施者が同じ応答を README の判定条件に照らす
- **THEN** 同じ合否になる

### Requirement: 失敗時の切り分け手段が示される

README は、skill または MCP がセッションから見えなかった場合の切り分け手段を示さなければならない（SHALL）。少なくとも、runner のログレベルを上げて起動時の警告を確認する方法と、host config の向き先が意図どおりかを確認する方法を含む（SHALL）。

#### Scenario: MCP が見えないときに原因へ辿り着ける

- **WHEN** セッションから MCP ツールが見えない
- **THEN** README に従って runner の起動ログを確認し、設定が読み込まれなかったのか型が認識されなかったのかを区別できる

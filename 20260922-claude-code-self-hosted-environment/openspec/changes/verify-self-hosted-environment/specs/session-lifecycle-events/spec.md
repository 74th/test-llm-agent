# Spec Delta

## Purpose

セッション毎ワークスペースの永続化を将来実装できるかを判断するため、runner とセッションのライフサイクル上でどのイベントが取れ、そこで何が参照できるかを記録に残すための要件を定める。永続化そのものはここでは実装しない。

## ADDED Requirements

### Requirement: 永続化は実装せずイベントの観測にとどめる

この change は、ライフサイクルイベントの発火と、その時点で参照できる情報を記録するところまでを対象とする。ワークスペースの保存・復元を実装してはならない（MUST NOT）。フックはログを書く以外の副作用を持ってはならない（MUST NOT）。

#### Scenario: セッションの結果が変わらない

- **WHEN** イベントログのフックを有効にしてセッションを実行する
- **THEN** フックを無効にした場合とセッションの結果が変わらない

#### Scenario: ワークスペースが保存されない

- **WHEN** 未コミットの変更を残したままセッションを終了させる
- **THEN** その変更はどこにも保存されず、ログには「保存可能だったか」の記録だけが残る

### Requirement: イベントがホスト側の追記ログに残る

すべてのイベントは、コンテナの寿命を超えて残る単一のログファイルに追記されなければならない（SHALL）。1 イベントが 1 行の JSON として記録され、少なくとも発生時刻・イベント名・セッション識別子を含む（SHALL）。

使い捨てのワークロードで実行された場合も、ログは失われてはならない（MUST NOT）。

#### Scenario: モードによらず同じログに集まる

- **WHEN** 常駐モードとセッション毎モードでそれぞれセッションを実行する
- **THEN** どちらのイベントも同じログファイルに追記されている

#### Scenario: ワークロード破棄後もログが残る

- **WHEN** セッション毎モードのワークロードが破棄されたあとにログを読む
- **THEN** そのセッションのイベントが残っている

#### Scenario: 1 行 1 イベントとして読める

- **WHEN** ログファイルを 1 行ずつ JSON として解析する
- **THEN** すべての行が解析でき、時刻・イベント名・セッション識別子を持つ

### Requirement: 秘密情報がログに書かれない

イベントログに、work-order JWT、セッションアクセストークン、GitHub トークン、GCP サービスアカウントキーの値が含まれてはならない（MUST NOT）。

#### Scenario: ログに秘密が出ない

- **WHEN** 検証を一通り実行したあとのログ全体を走査する
- **THEN** これらの資格情報の値が見つからない

### Requirement: runner レベルのイベントが観測される

runner のライフサイクル上の各段階でイベントが記録されなければならない（SHALL）。少なくとも、セッション毎モードでのワークロード起動要求、セッション開始、セッション終了を含む（SHALL）。

#### Scenario: 1 セッションの流れが追える

- **WHEN** 1 つのセッションを開始から終了まで実行してログを読む
- **THEN** そのセッション識別子で、開始から終了までのイベントが時系列に並んでいる

### Requirement: セッション終了イベントが永続化の判断材料を残す

セッション終了イベントは、その時点でワークスペースを保存できたかを後から判断できる情報を記録しなければならない（SHALL）。少なくとも次を含む（SHALL）: 終了理由、セッションの作業ツリーのパス、各パスがその時点で存在するか、未コミットの変更があるか、フック自身の所要時間。

#### Scenario: 救えたはずかが分かる

- **WHEN** 未コミットの変更を残してセッションを終了させ、ログを読む
- **THEN** 作業ツリーがまだ存在していたことと、未コミットの変更があったことが記録されている

#### Scenario: 終了理由が記録される

- **WHEN** 正常終了・異常終了・runner による中断のそれぞれを起こす
- **THEN** それぞれの終了理由がログに記録される

#### Scenario: 制限時間に収まるかが分かる

- **WHEN** セッション終了イベントのログを読む
- **THEN** フックの所要時間が記録されており、既定のタイムアウトに対する余裕が判断できる

### Requirement: セッション内のイベントでスクリプトが実行できる

runner が異常終了した場合にセッション終了イベントは発火しないため、その代替手段としてセッション内のイベントでスクリプトを実行できることが確認されなければならない（SHALL）。少なくとも、セッション開始・ツール実行後・応答完了・セッション終了の各時点で任意のスクリプトが走ることを確認する（SHALL）。

#### Scenario: ツール実行のたびにスクリプトが走る

- **WHEN** セッション内で Claude が複数回ツールを実行する
- **THEN** その回数に応じたイベントがログに記録される

#### Scenario: 定期スナップショットが成立しうると分かる

- **WHEN** セッション内イベントのログを読む
- **THEN** セッションの途中で任意のスクリプトを走らせられることが確認でき、定期スナップショットの実装可能性を判断できる

### Requirement: チェックアウト段階への介入可否が確認される

リポジトリ準備の段階に自前のスクリプトを差し込めるかが確認されなければならない（SHALL）。この確認は、組み込みのクローンを置き換えることになるため、本編の 2 モードとは切り離した単独の検証として行われる（SHALL）。

#### Scenario: チェックアウトに介入できる

- **WHEN** チェックアウト段階のフックを有効にしたセッションを実行する
- **THEN** そのフックが呼ばれたことがログに記録され、セッションは作業ツリーを得て動作する

#### Scenario: 常設できない理由が記録される

- **WHEN** 検証結果をまとめる
- **THEN** このフックが組み込みのクローンを置き換えること、および本編の git 認証方式と両立しないことが記録されている
